A single-slice issue that `/to-issues <ref>` rewrites in place with a blocker therefore reads as unblocked, and `next` (`selectDispatchable`) hands it out before its blocker is done.
- override-blanks-env: `detect_ecosystem` (`lib/checks/gen-override.sh:143-178`) writes name-only `HTTPS_PROXY`, CA-variable (`NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`) and `NPM_TOKEN` entries into crew's override unconditionally. The override is the last `-f`, so when the invoking shell does not set one of those names, the entry replaces the value the project's own compose file gives that variable with an empty/unset one: a project that sets its own proxy, CA path or registry token in compose loses it in every service crew runs.
- yarn-proxy-warning: the node passthrough `YARN_HTTPS_PROXY=${HTTPS_PROXY}` (`lib/checks/gen-override.sh:143`) is interpolated by compose; outside a proxied sandbox `HTTPS_PROXY` is unset, so every compose call that loads the override (every docker-mode `run.sh` command, through the shim) prints `The "HTTPS_PROXY" variable is not set. Defaulting to a blank string.`
- negative-grep-cannot-fail: the B9 test "HTTPS_PROXY set in the invoking shell does not write its value into the override" (`tests/dep-install-gen-override-proxy.bats:97-98`) asserts `! grep -q 'proxy.invalid'` and then `! grep -q '/secret/ca.pem'`; bash's errexit ignores a `!`-negated command, so the first, mid-test, can never fail the test (it passes even when the override carries the proxy URL), and the second fails it only because it happens to be the last line.

## Reference judgement

rewrite-blocked-by-unread: since this change, `issues-deps.json` is the only blocker source for a local issue (`parseIssue` reads `deps[file]`, absent = `[]`; the prose parser is gone). `publish-issues` writes that file; `rewrite`, the path to-issues step 6 takes for a source issue that stays one slice, writes only the body. So the rewritten issue's `## Blocked by` is never read by `next`/`features`, and solve-feature dispatches it ahead of (or alongside) its blocker; at best solve-issue's preflight prose check then stops the coder with `BLOCKED: depends on`. The fix (`325d3ce9`) makes `rewrite` set the issue's `issues-deps.json` entry from its new `## Blocked by`. Background, not a condition: PRD D7 made the JSON the only source and did not name `rewrite`. Caught if a finding says local `rewrite` (or `rewriteIssue`) leaves `issues-deps.json` without the new blockers, so the issue is dispatched or counted ready while blocked (or its blocker is ignored by `next`). A finding only about `rewriteBlockedBy`'s ref resolution, or about the GitHub tracker, is not it.

override-blanks-env: compose merges the override's `environment:` over the project's; a name-only entry for a variable the invoking shell does not set yields it unset/empty in the container rather than leaving the project's value. Outside a sandbox (the common case) every node project with its own `NODE_EXTRA_CA_CERTS`/`HTTPS_PROXY`/`NPM_TOKEN` in compose, and every python or other project with its own `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`/`HTTPS_PROXY`, loses it, so installs behind a corporate proxy or private registry fail. The fix writes an entry only when the generating shell sets that name. Background, not a condition: PRD D16 asserted that compose ignores name-only entries for unset variables, which is the wrong premise. Caught if a finding says an unset name-only passthrough entry in the override overrides (blanks, clears, unsets) a value the project's own compose file sets, for at least one of these variables. "Name-only entries leak nothing", or a finding about the CA mount, is not it.

yarn-proxy-warning: `${HTTPS_PROXY}` without a default makes compose warn whenever `HTTPS_PROXY` is unset, which is every docker-mode command run outside a proxy (and the entry also sets `YARN_HTTPS_PROXY` to blank). The fix is `${HTTPS_PROXY:-}`. Background, not a condition: PRD D16 prescribes `YARN_HTTPS_PROXY=${HTTPS_PROXY}` verbatim. Caught if a finding says the `YARN_HTTPS_PROXY=${HTTPS_PROXY}` entry makes compose warn (or interpolate a blank with a warning) when `HTTPS_PROXY` is unset. A finding that only says it blanks a project's `YARN_HTTPS_PROXY` counts for override-blanks-env, not this one.

negative-grep-cannot-fail: bats runs a test body under errexit, and bash exempts a `!` pipeline from it, so a `! cmd` that is not the test's last command never fails the test. Line 97 (`! grep -q 'proxy.invalid'`) is mid-test: the test meant to prove no proxy value is written into the override proves nothing about the proxy. Line 98 is the body's last command, so its status is the test's, until a line is added after it. The fix adds `|| false` to both, as the repo's other tests do. Background: it is B9's test. Caught if a finding names this test or its `! grep` lines and says a negated grep there cannot fail the test (errexit / bats ignores `!` mid-test), or that it needs `|| false` / `run` plus a status check. A finding that the test is missing or weak for another reason is not it.

Feature: simplify-codebase

### Problem Statement

Actor: a maintainer of this repo, and the agent sessions that read its skills and scripts.

Five read-only audits (2026-10-17) found about 4,000 lines that no live caller reaches, that duplicate a check another component already makes, that parse prose an LLM wrote, or that pin flags removed in earlier releases. Every one of those lines is read by whoever changes the file next, by the coder subagent whose context holds the SKILL.md, and by CI on every push. The repo's own rule (CLAUDE.md, "solve-feature and crew-review stay boring") says a line earns its place as a step or as a guard without which a person is misled or stuck; these lines do neither.

### Solution

One pass that removes or merges them, area by area, with no change to what a user of the pipeline sees except the four product decisions the user made: `## Requires` goes, `/address-pr-comments --auto` and the crew-rework workflow go, the pre-publish linter is replaced by refusals inside `publish-issues`, and Windows is served by WSL2 only. Docker mode, domain-modeling and the registry-credentials step stay; the last is renamed `registry_auth`. One restore rides along: the sandbox proxy and CA passthrough that #484 cut, so docker-mode installs work again from inside a proxied agent sandbox.

### Compatibility & Migration

- Sandbox passthrough (D16): additive; an override generated outside a sandbox gains name-only `environment` lines that compose ignores when the variables are unset, and no CA mount.

- `## Requires` (D5): an existing issue with the section is still valid markdown; the section is simply ignored. Issues in this repo and the demo have none.
- `--auto` / crew-rework (D9): a consumer repo with `crew-rework.yml` installed gets a failing workflow (`--auto` is an unknown flag); the CHANGELOG Breaking entry names the file to delete.
