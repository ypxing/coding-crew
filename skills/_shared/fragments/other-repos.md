**Other repos.** Inside a repo, design for that repo alone unless the user names another repo; never ask whether other repos are involved. For each repo the user names, use the path they gave, and ask for its path only when they named a repo without one. A path relative to the folder you run in, such as just the folder name, is fine; record it as an absolute path, so a later run from another folder still finds it. Explore each other checkout read-only, as you explore this repo — read, grep, run read-only commands; never edit, install or commit there — and cite its facts as `<checkout>/<file>:<line>`. Your summary of the design then lists every repo, this one first, one line each: its remote (`owner/repo`, from `git -C <checkout> remote get-url origin`; omitted when it has none), its checkout path, and what changes there.

**From a folder that is no git repo.** Use the repos the user named; when they named none, ask which repos the plan changes. With more than one and no word on which holds the feature's plan and issues (the **home repo**), ask in one line; list it first. Run every tracker op inside its repo (`cd <repo> && node <tracker CLI> <op> …`): the CLI refuses to run outside one, and `--main-root` alone does not do it: `gh` still runs in the working directory. Fetch a tracker ref in the repo the user names with it; for a ref with no repo, ask which repo first.
