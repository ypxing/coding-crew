# Docker Install

Use this when the dev commands file's `install_mode` is `docker`.
Do **not** run any command on the host — everything runs inside the container.

`PROJECT_ROOT` is established at session startup by the caller. Each bash tool call runs in a fresh shell — variables do not persist between calls. At the top of every bash call, assign it to its literal value from session startup:

```bash
PROJECT_ROOT="/absolute/path/to/checkout"
```

## Never

- Never run any install or project command on the host — everything runs inside the container.
- Never use `docker-compose` (v1 hyphenated binary) — always use `docker compose` (v2 plugin).
- **Use `docker compose` as usual.** Crew puts a `docker` shim first on `PATH`; it adds this checkout's override — `<git dir>/crew-compose.override.yml`, generated by `gen-override.sh` — as the last `-f` of every `docker compose` call, with or without `-f` of your own, and `run.sh` calls it for you. Do not add the override, `-p` or git-env `-e` flags yourself: the override already names this checkout's compose project and carries its `GIT_DIR`/`GIT_COMMON_DIR`.
- **Never write the override manually** — always generate it via `gen-override.sh`. Hand-writing the file produces volume names that do not carry the lockfile hash. Nothing named `docker-compose.override.yml` is ever written into the repo; a project's own committed one is loaded unchanged, ahead of crew's.
- **In your own terminal** (a human, outside an agent session) put the shim on `PATH` once, so a bare `docker compose` there loads the override too: `export PATH="<skill-dir>/scripts/checks/shim:$PATH"`.

## Steps

Each checkout is its own compose project with its own dependency volumes, named by a hash of its
manifests and lockfiles (`wt_<proj>_<owner4>_<eco>_<dir>_<lock8>`). `docker-install.sh` installs only
when the volumes it names have no completion stamp, so a repeat call against unchanged lockfiles runs
no install command. Still apply the retry rule if a later command fails with a module-not-found
error: a package installed into the volume since the stamp was written (an in-container `npm install
foo`) is not in the lockfile, and `--force` reinstalls.

`docker-install.sh` reads `docker_service`, `install` and `credential_target` from
the dev commands file itself (`scripts/checks/commands-file.sh` names it). Steps 0 and 1 fill in the last two when nobody
has looked yet.

### 0. Credential target — only when the cache has none

```bash
CACHE=$(bash "<skill-dir>/scripts/checks/commands-file.sh" --project-root "$PROJECT_ROOT")
RAW=""
[ -f "$CACHE" ] && RAW=$(grep -o '"credential_target"[[:space:]]*:[[:space:]]*\("[^"]*"\|null\)' "$CACHE" | head -1)
```

`$RAW` non-empty (a command, or `null`: someone already looked) — skip to step 1. Empty — read the
Makefile (`$PROJECT_ROOT/Makefile`), if present, for:

- Targets that generate package-manager credential config files (e.g. `.npmrc`, `.yarnrc.yml`,
  `pip.conf`, `.cargo/credentials.toml`) via `envsubst`, `echo`, or template files
  (`.npmrc.tpl`, `pip.conf.tpl`, etc.)
- Comments describing required secrets, so you recognise a target's *purpose* even when its
  name alone does not say so

Persist whatever you conclude — the full command (e.g. `make _registry`, not just the bare target
name), or a confident `null`:

```bash
cat > "$PROJECT_ROOT/.credential-target-discovery.json" <<'JSON'
{"credential_target": "<the command you found, e.g. \"make _registry\", or null if you checked and found none>"}
JSON
(cd "$PROJECT_ROOT" && bash "<skill-dir>/scripts/checks/write-commands-cache.sh" --response-file .credential-target-discovery.json)
rm -f "$PROJECT_ROOT/.credential-target-discovery.json"
```

**Never read the contents of `.env*` or any credential config file** — not to log, not to inspect, not to verify.

### 1. Install command — only when the cache has none

```bash
RAW=""
[ -f "$CACHE" ] && RAW=$(grep -o '"install"[[:space:]]*:[[:space:]]*\("[^"]*"\|null\)' "$CACHE" | head -1)
```

`$RAW` non-empty — skip to step 2. Empty — check whether the Makefile has a public `install`/`deps`
target whose recipe runs the package manager *inside the container* (no `docker` call of its own) in
every subdirectory that has a named volume, not just the root. Persist that target invocation (e.g.
`make install`), or `null`:

```bash
cat > "$PROJECT_ROOT/.install-discovery.json" <<'JSON'
{"install": "<the command you found, or null>"}
JSON
(cd "$PROJECT_ROOT" && bash "<skill-dir>/scripts/checks/write-commands-cache.sh" --response-file .install-discovery.json)
rm -f "$PROJECT_ROOT/.install-discovery.json"
```

### 2. Run `docker-install.sh`

```bash
bash "<skill-dir>/scripts/checks/docker-install.sh" --project-root "$PROJECT_ROOT" \
  --timeout 1800 \
  # only on a module-not-found retry: delete the stamp, then reinstall
  --force
```

It ensures `.env`, generates this checkout's override, and runs the install command (the cached
`install`, else each manifest directory's lockfile command) in the service, unless the root
dependency volume's `.crew-stamp` says it already ran. Handle its exit code:

- **0** — the volumes hold the install: it ran, or the stamp was already there (it prints
  `Present: …`). Continue to step 3.
- **2** — nothing this mechanism could do here (no compose file, no service, no supported
  ecosystem). Report this plainly rather than guessing a workaround.
- **3** — the install command failed inside the container (no stamp was written). Report `BLOCKED`
  with the tail of output it prints to stderr.
- **5** — the cached `install` command runs docker itself, which the container has none of. Report
  `BLOCKED` with its message — the fix is a container-side command in the dev commands file's
  `install`, not in this session.

Every failure ends with `docker-install: failed — service <s>, step <step>, exit <n>` and removes the
override, so the next `run.sh` call installs again rather than run against empty volumes.

### 3. Run every later command through `run.sh`

Every test, lint and type-check run from here on goes through `run.sh`, which builds the
`docker compose run --rm <service>` invocation for you, through the shim — and runs a command whose
own recipe already calls docker on the host instead of nesting it (its own `docker compose` calls get
the override from the shim too):

```bash
bash "<skill-dir>/scripts/checks/run.sh" --project-root "$PROJECT_ROOT" -- "<command>"
```

Never hand-build that `docker compose` command for a check. Any other ad-hoc command, a one-off
`docker compose` one included, goes through `run.sh -- <cmd>` the same way.

## Install failures

If install fails because the container's entrypoint ignores the command, check the compose file for an `entrypoint:` key and override it:

```bash
PATH="<skill-dir>/scripts/checks/shim:$PATH" docker compose \
  run --rm --entrypoint sh <service> -c "<install-command>"
```

If install fails due to missing auth tokens, network errors, or Docker not running — stop immediately and report blocked with the verbatim error. Do not attempt workarounds.

If install fails with `fatal: not a git repository: .../worktrees/<name>` from a postinstall hook (lefthook, husky, simple-git-hooks, etc.), that is a linked worktree's `.git` file pointing at an absolute host path the container can't see. `gen-override.sh` already mounts the repo's shared `.git` read-only in the override (`/git-common`, plus writable `hooks/` and `info/` overlays for the hook installer's own writes there) and sets this worktree's `GIT_DIR`/`GIT_COMMON_DIR` in it; the failure almost always means the call did not go through the shim, so the override was never loaded — check that the shim dir is first on `PATH` (`command -v docker`) and that `<git dir>/crew-compose.override.yml` exists (re-run `gen-override.sh` if not). If it was loaded and the failure persists, the project's tooling is likely resolving git some other way (e.g. `GIT_WORK_TREE`, a submodule) that `GIT_DIR`/`GIT_COMMON_DIR` don't cover. Report blocked with the verbatim error rather than hand-editing the override.

In a linked worktree, `error: could not lock config file /git-common/config: Read-only file system` from husky (or any installer running `git config`) is expected and harmless: the shared `.git/config` is mounted read-only on purpose, the installer ignores that exit code, and hooks never run in the container. Only a non-zero install exit is a failure.
