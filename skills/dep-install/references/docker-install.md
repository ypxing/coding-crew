# Docker Install

Use this when the dev commands file's `install_mode` is `docker`.
Do **not** run any command on the host — everything runs inside the container, except a command that runs docker
itself, which `docker-install.sh` and `run.sh` run on the host for you.

`PROJECT_ROOT` is established at session startup by the caller. Each bash tool call runs in a fresh shell — variables do not persist between calls. At the top of every bash call, assign it to its literal value from session startup:

```bash
PROJECT_ROOT="/absolute/path/to/checkout"
```

## Never

- Never run any install or project command on the host yourself — `docker-install.sh` and `run.sh` decide where it runs.
- Never use `docker-compose` (v1 hyphenated binary) — always use `docker compose` (v2 plugin).
- **Use `docker compose` as usual.** Crew puts a `docker` shim first on `PATH`; it adds this checkout's override — `<git dir>/crew-compose.override.yml`, generated by `gen-override.sh` — as the last `-f` of every `docker compose` call, with or without `-f` of your own, and `run.sh` calls it for you. Do not add the override, `-p` or git-env `-e` flags yourself: the override already names this checkout's compose project and carries its `GIT_DIR`/`GIT_COMMON_DIR`. It also passes the proxy, CA and token variables (`HTTPS_PROXY`, `NPM_TOKEN`, …) that were set when it was generated, with their values read from your shell at each call; after setting or unsetting one of them, re-run `docker-install.sh` (no `--force`) to regenerate it.
- **Never write the override manually** — always generate it via `gen-override.sh`. Hand-writing the file produces volume names that do not carry the lockfile hash. Nothing named `docker-compose.override.yml` is ever written into the repo; a project's own committed one is loaded unchanged, ahead of crew's.
- **In your own terminal** (a human, outside an agent session) put the shim on `PATH` once, so a bare `docker compose` there loads the override too: `export PATH="<skill-dir>/scripts/checks/shim:$PATH"`.

## Steps

Each checkout is its own compose project with its own dependency volumes, named by a hash of its
manifests and lockfiles (`wt_<proj>_<owner4>_<eco>_<dir>_<lock8>`). `docker-install.sh` installs only
when the volumes it names have no completion stamp, so a repeat call against unchanged lockfiles runs
no install command. Still apply the retry rule if a later command fails with a module-not-found
error: a package installed into the volume since the stamp was written (an in-container `npm install
foo`) is not in the lockfile, and `--force` reinstalls.

Each call also removes the repo's dependency volumes no live checkout's override names (`prune-volumes.sh`):
a removed worktree's, and a checkout's own from before its lockfile changed. Only volumes an override of this
repo named are touched, and one a container has mounted is left for the next call.

`docker-install.sh` reads `docker_service`, `install` and `registry_auth` from the dev commands
file itself (`scripts/checks/commands-file.sh` names it); dep-install's Step 1 has already made sure
they were asked. Do not look for an install command or a registry auth command yourself.

### 1. Run `docker-install.sh`

```bash
bash "<skill-dir>/scripts/checks/docker-install.sh" --project-root "$PROJECT_ROOT" --timeout 1800
```

Only on a module-not-found retry, delete the stamp and reinstall:

```bash
bash "<skill-dir>/scripts/checks/docker-install.sh" --project-root "$PROJECT_ROOT" --timeout 1800 --force
```

It ensures `.env`, generates this checkout's override, and runs the install command (the dev commands file's
`install`, else each manifest directory's lockfile command) in the service, unless the root
dependency volume's `.crew-stamp` says it already ran. An `install` that runs docker itself (a
`make deps` wrapping `docker compose run`) runs on the host, as `run.sh` runs such a check, and its
compose calls get the override. Handle its exit code:

- **0** — the volumes hold the install: it ran, or the stamp was already there (it prints
  `Present: …`). Continue to step 2.
- **2** — nothing this mechanism could do here (no compose file, no service, no supported
  ecosystem). Report this plainly rather than guessing a workaround.
- **3** — the install command failed (no stamp was written). Report `BLOCKED` with the tail of
  output it prints to stderr.

Every failure ends with `docker-install: failed — service <s>, step <step>, exit <n>` and removes the
override, so the next `run.sh` call installs again rather than run against empty volumes.

### 2. Run every later command through `run.sh`

Every test, lint and type-check run from here on goes through `run.sh`, which builds the
`docker compose run --rm <service>` invocation for you, through the shim — and runs a command whose
own recipe already calls docker on the host instead of nesting it (its own `docker compose` calls get
the override from the shim too):

```bash
bash "<skill-dir>/scripts/checks/run.sh" --project-root "$PROJECT_ROOT" -- "<command>"
```

Never hand-build that `docker compose` command for a check. Any other ad-hoc command, a one-off
`docker compose` one included, goes through `run.sh -- <cmd>` the same way.
